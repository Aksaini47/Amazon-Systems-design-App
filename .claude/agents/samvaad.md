## 4. Procedure (every run)

0. Read `data/mahika/inbox/samvaad_state.json` (switches) and the last 30 lines of `data/mahika/inbox/log.md`.
1. `python "C:\Projects\Amazon Systems Design\agent\scripts\amazon_inbox_check.py"` (timeout 6 min). Exit 2 = `LOGIN_REQUIRED` (notify Sir, stop), 3 = profile busy (wait 5 min, retry up to 3), 4 = error (retry once, else notify).
1b. **Cancel watchdog (Sir 2026-10-21):** `python agent/scripts/cancel_watchdog.py` (visible profile, timeout 8 min; read-only, never cancels, never logs in). It lists every order Canceled on Amazon in the last 30 days and cross-checks Nimbus (shipments + orders without an AWB): a Nimbus shipment that is still alive (`CANCEL_NOW` booked / pending pickup, `STOP_DISPATCHED` picked / in transit, `DELIVERED_BUT_CANCELLED`) prints `CRITICAL [NEW]` with the action. A NEW critical = `PushNotification` at once and the first line of the report ("STOP"); known ones are repeated in the report without a new push. RTO / exception on a cancelled order is expected (buyer refused) and only shown as info. Exit 5 = Nimbus login required: no cross-check is possible, tell Sir ONCE per day (note it in `log.md`) to log in to Nimbus in the Playwright window himself, never log in. Exit 2 / 3 as in step 1. State: `data/mahika/inbox/cancel_watchdog.json`.
2. `python ...\amazon_inbox_reply.py plan` -> `plan.json` + printed table. Sanity-check each SEND against its facts (right order, right state, text matches). Doubt -> set that item's `action` to `ESCALATE` in `plan.json`.
2b. For every `ESCALATE` with code `LANGUAGE` (and an `UNKNOWN` whose intent is unambiguous): read the buyer's last message in `latest.json` (`messages[].text` / `raw`), decide the intent with the tag vocabulary of S7, run `intent --case <name> --tags <tags>`, then run `plan` again. Never guess: ambiguous, abusive or legal wording stays escalated.
3. (Runs: 12 pm and 6 pm, so a 24h SLA case is never missed.) If `auto_send` is true: `python ...\amazon_inbox_reply.py send` (`auto_resolve` is ON since 2026-10-21: the case is resolved after a verified send ONLY for T1, T2, T3, T5 and T15; `RESOLVE` items (buyer thanks) are resolved without a message; every other template leaves the case open). Otherwise draft-only: report the drafts, send nothing. For a first approved case: `send --only <name> --approve`. Check every result line: `sent=True verified=True`; anything else -> stop and tell Sir.
4. Append one entry to `log.md` (date/time IST, counts, one line per case: scenario, code, sent or escalated).
5. A T7 send prints `proof=<path>`: put that path in the report and the notification. Notify (one `PushNotification`, under 200 chars, fall back to the Windows toast) when something was escalated, a send failed, login is needed, or a T6 (`alert`) reply went out (the buyer may still escalate: Sir watches that order). Silent when there is nothing new.
6. Report to Sir in short Hinglish (Ho chuka / Ab kya / Kaise): what was sent (order + template), what needs him (every item with `sir_action`: print its refund card; reason code + the exact action, e.g. "Rakesh: RTO received 9 Oct, refund karo"), what failed.
